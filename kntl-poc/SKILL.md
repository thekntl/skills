# KNTL POC

`/kntl-poc #N` proves the value feature on ticket `#N (kısa ad)`, the POC ticket the map carries under `kntl:app-shell`; without an argument, take the open `kntl:app-shell` ticket whose title says POC. Second half of the gate before faces open: `/kntl-design` showed how the product looks, the POC shows it is feasible. The proof is a **tracer bullet**: one path through the real capability the promise rests on (the camera reads the label, the alarm fires, the model answers), end to end, on the real runtime, with no product backend. Owner-facing rules and tool access live in `docs/agents/kntl-conventions.md`; read it first.

## Preflight

1. The App Shell row of the Status table in `docs/design/DESIGN.md` reads foundation or done, and the Design Lab target builds and launches with its demo; otherwise say "Önce `/kntl-design` bitmeli." and stop.
2. The POC ticket `#N` is on the map (`kntl:app-shell` plus its `flow:` label) and the value feature it names is a `confirmed` entry in the ledger. A missing or `provisional` entry → call the Skill tool with `kntl-grilling` on "which single feature earns the promise" before anything else.

## Shape of the proof

- **Bare.** Default controls, default font, one screen whose only job is to show the raw result. Design arrives at integration, from `DESIGN.md`.
- **Home.** Its own `POC` section on the Design Lab home, beside the experiments and the demo, under version control: a tracer bullet that step 6 integrates, where `prototype` would build a throwaway on its own branch. The Lab layout per platform (where `POC/` sits) and its run command are in `kntl-design`'s `references/design-lab.md`; read it before adding the section. The Lab is removable, so the integration ticket from step 6 moves the proof into production before the Lab-removal ticket runs.
- **Real.** Every call reaches the real capability: the device sensor, the device SDK, the provider's API with the production model. Simulator when step 2 found the capability there; a physical device otherwise.
- **Client-only.** The proof calls devices and providers straight from the app or from a local script. A step that only works behind a server (a secret that cannot ship in the client, a webhook) becomes the `backend:` line of the `## Dependencies` list, which is what `/kntl-setup`'s backend question waits for.
- **Keys through the environment.** Source holds the variable name; the value lives in the scheme's environment or a git-ignored `.env`; the dependency line names where the key lives.
- **Prompts as files.** For an LLM feature the starting system prompts are one file per prompt inside the POC section, loaded at runtime, so integration moves files.

## Steps

1. **Pin the feature.** From the map and the ledger write the proof sentence, "the proof shows <actor> doing <action> through <capability chain> and the screen shows <raw result>", citing its `D-nnn`. Done when the sentence names one capability chain, the owner has confirmed it in one line, and any second candidate feature has its own ticket on the map.
2. **Verify before building.** For every capability in the chain establish from primary sources: availability on the target platform version; for a device capability the usage-string keys, entitlements, background modes, and whether the simulator supports it; for a provider the account, key, model, region availability, observed cost per call, and whether the key may ship in the client. Call the Skill tool with `research` when the answer lives outside the repo. Done when each capability has a source link and a drafted dependency line: what, who provides it (agent or owner), needed now or at setup.
3. **Collect what the proof needs now.** For each dependency marked "now" that is owner-only (a paid developer capability, an API key, a device signed for development) call the Skill tool with `wizard` and continue from the owner's output. Done when every "now" dependency is in hand: keys in the environment, device paired and trusted, capabilities enabled on the account.
4. **Build and run it.** Run the ticket through `/kntl-implement #N` with these overrides: tests cover only the seam that survives integration (parsing, prompt assembly, response mapping); smoke is the proof run on the runtime the Shape demands, raw result on screen, in place of the `SCENARIOS.md` walk, with evidence as `kntl-implement`'s `references/smoke.md` says; the PR's `## Outcome` carries the proof sentence and the run evidence; close is steps 5–6 of this skill in place of its step 8's last line, the Hikaye block stays. Done when the smoke evidence shows the proof sentence true on the real runtime, or shows exactly which link of the chain broke and how.
5. **Record.** Read `kntl-grilling`'s `references/ledger.md`, then append one entry per capability in the chain with its recipe: question "<capability> gerçek runtime'da çalışıyor mu?", the run's result as the answer, `face: "app-shell"`, `flow` the slug of `#N`'s `flow:` label, tags `["poc", "<capability>"]`, state `confirmed` when the run exercised it and `research-needed` when it could not, `evidence` the PR URL from step 4 (its `## Smoke on the real runtime` section; a `research-needed` entry names who looks at what instead, per that file). Then post one comment on `#N`: the `## Round N` block per that file, followed by `## Dependencies`: one line per dependency drafted in step 2, `<what> · provided by <agent|owner> · needed <now|at setup> · <D-id> · <source link>`; the `backend:` line when the Client-only rule produced one; and the POC section's path. Done when every capability has a ledger id, every dependency line from step 2 appears in the comment with its provider, timing, D-id and source link, and the comment names the POC section path.
6. **Close the gate.**
   - Proof true → file the integration ticket as a child of the map the way `docs/agents/issue-tracker.md` says: `kntl:app-shell`, `#N`'s `flow:` label, `ready-for-agent`; body per the conventions file, citing the POC section path, the proof sentence and its D-ids; blocked natively on the open App Shell foundation tickets, which `## Blocked by` names, since the proof lands on top of them; the stack wait is `/kntl-next`'s Faz gate. Edit the Lab-removal ticket's `## Blocked by` to name the integration ticket. The closing message ends with "Nasıl görüneceğini biliyoruz ve yapılabiliyor. Sıradaki: `/kntl-setup`."
   - Proof false → the failure is the result: the broken link's entry from step 5 carries the evidence. Call the Skill tool with `kntl-grilling` on the promise itself, then file the narrowed promise's POC ticket on the map with `kntl:app-shell`, its `flow:` label, `ready-for-human` and the new D-id. The closing message ends with "Sıradaki: `/kntl-poc #M`", naming that ticket.

   Done when `#N` is closed by its merged PR, the closing message carries the Hikaye block and ends with its branch's sentence, and either the integration ticket is on the map with those labels and blockers and the Lab-removal ticket lists it under `## Blocked by` (proof true), or the broken link's entry is in the ledger and the narrowed promise's POC ticket is on the map with `ready-for-human` (proof false).
